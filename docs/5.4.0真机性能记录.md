# WaferAI 5.4.0 真机性能记录

测试日期：2026-11-17。设备为 ROG Phone 8（ASUS_AI2401_A），Android 16 / API 36，8 核、约 16 GB 内存，USB 供电。同一部手机、同一份用户数据，覆盖安装切换对照包，不清空用户数据。

## 方法

使用 AndroidX Macrobenchmark 1.4.1，方法参考官方 [Macrobenchmark 概览](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-overview)及 [指标说明](https://developer.android.com/topic/performance/benchmarking/macrobenchmark-metrics)。项目中保留 `android/macrobenchmark` 测试模块和 app 的 `benchmark` 构建类型，便于复测。

对照为修改前的 5.3.0 源码快照，候选为 5.4.0。两者均使用相同签名的不可调试、可被分析的 benchmark 包，`CompilationMode.Full()`，每个场景 5 次。数据不来自模拟器，也不使用 debug 包比较帧耗时。Full 编译减少编译状态差异，不代表首次安装后未经优化的日常性能，本次未生成 Baseline Profile。

1. 冷启动使用 `StartupMode.COLD` 和 `StartupTimingMetric`，测量首帧及完全显示时间。两版均在开屏结束后报告完全显示，保留约 2.25 秒的开屏动画。
2. 切页使用 `FrameTimingMetric`，首页和其他页准备完成后，依次点击 AI → 数据 → 工具 → 晶圆，循环两次，点击间隔 700ms。旧版额外的「我的」也不纳入测试，以保持路线一致。
3. ROG 的系统无法在未运行的进程中接收清理着色器的广播，因此冷启动的准备阶段先打开应用再回桌面。随后由 Macrobenchmark 清理并终止进程，再测量新的冷启动；准备阶段的打开不计入结果。

最初一次对照运行的冷启动因上述广播问题失败，未作为有效启动数据；该次成功的切页结果来自 `baseline-tabs.json`，修正准备流程后通过的 5 次启动来自 `baseline-startup.json`。最终候选的两项测试同一次运行通过，来自 `final.json`。未使用中间优化轮次替代最终结果。

## 测量结果

时间单位均为 ms；启动使用 5 次的中位数，帧指标使用 Macrobenchmark 输出的分位数。

| 指标 | 5.3.0 对照 | 5.4.0 候选 |
| --- | ---: | ---: |
| 冷启动首帧 TTID | 210.722 | 199.548 |
| 冷启动完全显示 TTFD | 2479.029 | 2475.936 |
| 帧 CPU 耗时 P50 | 3.157 | 3.169 |
| 帧 CPU 耗时 P90 | 4.140 | 4.002 |
| 帧 CPU 耗时 P95 | 4.626 | 4.310 |
| 帧 CPU 耗时 P99 | 6.184 | 6.494 |
| 帧超时量 P50 | -7.677 | -7.438 |
| 帧超时量 P90 | -6.832 | -6.874 |
| 帧超时量 P95 | -6.148 | -6.512 |
| 帧超时量 P99 | -3.587 | -4.405 |

本轮首帧中位数减少约 5.3%，帧 CPU 的 P95 减少约 6.8%。完全显示时间基本不变，因为两版均包含同样的开屏动画。CPU P99 反而略高，不能据此声称所有切页、所有设备或所有长尾停顿都已改善。负的帧超时量表示相应分位的帧在截止时间前完成，不等同于全部帧零掉帧，也不能换算为固定 FPS。

## 对应修改

- `DockBackdrop.kt`：切页或背景取样不可用时直接绘制内容，避免仍然录制全屏图层。
- `MainActivity.kt`：底栏完全透明/完全不透明时跳过背景采样，保留中间透明度的玻璃取样。
- `ToolsScreen.kt`：工具页改为按需布局，减少屏幕外设置分组的首轮构建。

最终用户交付的是可覆盖安装的 debug 测试包，测量包为不可调试的 benchmark 包，二者运行开销不同；上述数值不直接承诺 debug 包的绝对耗时。测量完成后又增加一处备份恢复时清除旧队列的保护，该逻辑不在启动与切页的测量路径中。最终 debug 包重新构建并通过功能检查。
